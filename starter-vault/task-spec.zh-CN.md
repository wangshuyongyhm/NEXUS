# task-spec.md —— 任务书契约（通用模板）

> 每一份穿过调度总线的任务都是一份带七段的 Markdown。任务书是契约：
> 执行者按它执行，门禁按它校验，审计者由它复盘。占位符用 `<尖括号>`。

## 七段结构

### 1. 头部

```markdown
---
task_id: <唯一编号>
title: <一行标题>
target_agent: <执行者名>
priority: <P0|P1|P2>
---
```

### 2. 来源锚

### 2b. 参考资料

任务书旁放一份 `references.md`，携带本任务**实际**依赖的知识库命中——
先搜，贴真实内容，不是只贴标题。没有它执行者无法兑现「先查后动」。

这个任务为什么存在——决策、父任务、用户定向的链接。最多两行；
审计者必须一击到达源头。

### 3. 核心目标

完成后什么必须为真。写成结果，不是动作。
差的写法：「看看缓存」。好的写法：「夹具集上缓存命中率 ≥90%，用 <命令> 度量」。

### 4. 完成标准（可验证）

一份 checklist，每一项都能由一条命令或一个必须存在的文件来验证。
机器验不了的标准不属于这里——放到报告的讨论段去。

### 5. 禁止清单

明示的禁做项：不许碰的文件、已被否决的方案、范围边界。
执行者先读这段再读目标——它定义爆炸半径。

### 6. 已排除方案

至少两个考虑过又否决的方案，各带原因与证据。这一段拦住下一个 Agent
重走死路。这里空着=没思考过。

### 7. 陷阱地图

这类工作的至少三个已知坑，各带对策。来自知识库（写之前先搜）和
主控自己的伤疤。

## 产出登记

`done` 之前，执行者在任务书副本里补全产出登记：哪份报告、哪些文件、
哪个复现脚本——带链接。登记表就是 persist 门禁校验的索引。

## 机读尾块

每份 `output/report.md` 以 YAML 块收尾，让机器不用读散文就能消费结果：

```yaml
status: done | failed | partial
evidence:
  - <跑过的命令+输出，或文件路径+校验和>
next_steps:
  - <下一个任务该做什么>
```

## 修订

任务中途的变更走任务书：主控追加修订段（改了什么、为什么、什么作废）
并在总线重新登记。聊天里的口头纠偏是对话；任务书才是契约。
